# 基于金山云平台的 SRE 可靠性工程平台 —— 项目技术文档

> 本文档既是项目设计说明，也是面试讲解稿。每个设计决策都附「为什么这么选」与「面试可能怎么问」。

---

## 0. 一句话定位

用 Go 写一个电商订单微服务，在其上**端到端落地 SRE 可靠性工程方法论**——从 SLO 定义、可观测性三支柱、错误预算告警，到混沌工程验证与故障自愈，回答"SRE 到底在做什么"。

它不是"把服务部署起来"，而是"**用软件工程方法让系统天然更稳定、可量化、可自治**"。

---

## 1. 为什么做这个项目

### 1.1 痛点
传统运维的稳定性是"感觉"——"好像挺稳"、"最近没出事"。出了故障靠人工经验排查，没有量化目标，没有预算概念，告警靠拍阈值（CPU>80% 就报），结果要么告警疲劳、要么漏报。

### 1.2 SRE 的回答（四问）
| 问题 | SRE 的回答 | 本项目对应模块 |
|---|---|---|
| 系统有多稳？ | 用 SLO 与错误预算量化 | SLO 引擎 |
| 不稳了怎么第一时间知道？ | 可观测性三支柱 + 燃烧率告警 | Prometheus/Loki/Jaeger + 告警规则 |
| 故障来了能不能自己扛？ | 探针自愈 + HPA 弹性 + 熔断 | K8s Probe + HPA |
| 怎么主动验证它扛得住？ | 混沌工程 | Chaos Mesh |

### 设计原则
- **数据面/控制面分离**：业务端口 8080、指标端口 9090 分开，避免采集流量影响业务。
- **应用与后端解耦**：应用只认 OTLP Collector，换存储后端（Jaeger→Tempo）不动业务代码。
- **全声明式**：一切基础设施用 YAML 描述，可复现、可版本控制、可 diff。

### 金山云基础设施（云平台落地）
本项目跑在金山云真实多节点集群，非本地 demo：
- **KEC 主机**：5 台（3 master + 2 node），Rocky 9.8 / K8s v1.31.14 / containerd 2.2.6 / Calico CNI（Pod CIDR 172.16.0.0/16，Service CIDR 192.168.0.0/16）。
- **VPC + EIP + 安全组**：5 节点内网 10.0.0.x 互通；公网经 EIP 访问，安全组放行 NodePort 30088/30090/30300/30686。
- **金山云 KECR**（`hub.kce.ksyun.com`）：自研 ordersvc 镜像 push 至私有仓库，集群经 `imagePullSecrets` 拉取，体现私有镜像仓库治理与凭证管理。
- **金山云 KS3**：Loki chunks 落 KS3（S3 兼容 API），实现日志存算分离与长期归档（见 `observability/loki/loki.yaml`）。
- **local-path StorageClass**：集群自带 default SC，供 Loki 索引等本地持久化。
- **containerd 镜像加速**：5 节点统一配置 `certs.d` 加速 docker.io 与 ghcr.io（Chaos Mesh 镜像在 ghcr.io），解决国内拉取超时。
- **kubeconfig 公网化**：admin.conf 的 server 由内网 VIP `10.0.0.236:16443`（haproxy 高可用入口）改为 master01 公网 `10.0.0.182:16443`，本地 kubectl/helm 直连集群（证书 SAN 不含公网 IP，用 `insecure-skip-tls-verify`，demo 用法）。

## 4. SLO 设计（项目核心，面试必问）

### 4.1 SLI 与目标
| SLI | 定义 | 目标(30d) | 错误预算 |
|---|---|---|---|
| 可用性 | 非 5xx 请求占比 | 99.9% | 0.1% ≈ 43 分钟/月 |
| 延迟 | P99 请求延迟 | < 500ms | — |

> **面试点**：为什么是 99.9% 而不是 100%？——SRE 认为 100% 是错误目标，过高的 SLO 意味着过高的研发/资源成本且无创新空间。留出错误预算，允许小故障，团队才能在预算内做发布、做实验。

### 4.2 错误预算
- 允许错误率 = 1 − SLO = 0.1%
- 月错误预算 = 43200 分钟 × 0.1% ≈ 43 分钟
- 预算用来做什么：消耗预算做新版本发布、做混沌实验；预算耗尽则冻结变更、专心保稳。

### 4.3 燃烧率（Burn Rate）
**燃烧率 = 实际错误率 / 允许错误率**

- = 1：按预算匀速消耗（43 分钟耗尽月预算）
- = 14.4：1 小时耗尽 2% 月预算 → 真实业务受损，需立即介入
- = 6：6 小时消耗 ~5% → 持续劣化，建工单

### 4.4 多窗口多燃烧率告警（Google SRE《SRE 工作手册》第 5 章）

| 告警 | 短窗口 & 长窗口 | 阈值 | 含义 | 动作 |
|---|---|---|---|---|
| Page | 5m & 1h | > 14.4 | 1h 消耗 ≥2% 月预算 | 立即介入 |
| Ticket | 30m & 6h | > 6 | 6h 消耗 ~5% 月预算 | 建工单 |
| Budget | 1d | > 1 | 按此速率将耗尽预算 | 排期优化 |

> **面试点**：为什么要双窗口（短+长）？——短窗口（5m）负责"快速发现"，长窗口（1h）负责"防抖降噪"。两者**同时**超阈值才告警，既灵敏又不抖动。单窗口要么太灵敏（误报多）要么太迟钝（漏报）。

> **面试点**：为什么用 Recording Rules 预聚合？——告警查询时若直接扫原始 counter 序列会全量计算，压力大。先把 5m/1h/6h/1d 的比率预录制成新指标，告警只查预制指标，查询从 O(全量) 降到 O(1)。

## 5. 可观测性三支柱

### 5.1 Metrics（指标）—— ordersvc 自定义 6 类
| 指标 | 类型 | 用途 |
|---|---|---|
| ordersvc_http_requests_total | Counter | 可用性 SLI 分子分母 |
| ordersvc_http_request_duration_seconds | Histogram | 延迟 SLI（P99） |
| ordersvc_orders_in_flight | Gauge | HPA 扩缩容依据 |
| ordersvc_orders_created_total | Counter | 业务成功量 |
| ordersvc_orders_failed_total | Counter | 失败分类统计 |
| ordersvc_failure_rate_injected | Gauge | 混沌注入强度可视化 |

> **面试点**：为什么用专用 Registry 而非默认？——隔离 Go runtime/进程指标噪声，只暴露对 SLO 有用的指标，避免指标爆炸。

### 5.2 Logs（日志）—— Loki + Promtail
- Promtail 以 **DaemonSet** 跑在每个节点，采 `/var/log/pods/*.log`
- 自动打 `namespace/pod/container` 标签
- pipeline_stages 解析 ordersvc 结构化 JSON 日志，提取 `level` 标签便于按级别过滤

### 5.3 Traces（链路）—— OTel + Jaeger
- ordersvc 用 otel SDK 在 `createOrder` 内建 span，下游调用建子 span `downstream.payment`
- 通过 OTLP/HTTP 上报 Collector(4318)，Collector 转发 Jaeger(4317)
- Collector 配 `memory_limiter` + `batch` processor：采样限流防突发 trace 压垮后端

> **面试点**：为什么应用不直接发 Jaeger？——Collector 解耦，换后端只改 Collector 配置不动业务；且 Collector 能做采样/限流/重试，是可观测性成本治理的关键。

## 6. 混沌工程

每个实验对应一个**可靠性假设**，验证系统在故障下仍满足 SLO：

| 实验 | 类型 | 假设 | 验证 |
|---|---|---|---|
| Pod Kill | PodChaos | 随机杀 Pod，30s 内自愈，SLO 不击穿 | Deployment 自动重建 + readiness 摘流量 |
| Network Delay 200ms | NetworkChaos | P99 延迟告警触发，服务仍可用 | 延迟 SLO 告警链路 |
| CPU Stress 80% | StressChaos | HPA 触发扩容 3→N，CPU 回落 | HPA 基于 CPU 利用率弹性 |
| HTTP 50% 5xx | /admin/fault | 错误预算燃烧率告警触发 | 多窗口燃烧率告警 |

### 6.5 变更安全：金丝雀发布与自动回滚（Argo Rollouts）

变更（发布）是 80% 故障的来源。项目用 Argo Rollouts 把 ordersvc 从原生 Deployment 升级为 Rollout，实现**渐进式交付 + SLO 驱动自动回滚**，把"发布是否健康"从人肉看大盘变成指标驱动的自动决策：

- **金丝雀策略**：20% → 40% → 60% → 100% 流量逐步切到新版本，每步 pause 跑 AnalysisTemplate。故障被限制在 20% 流量内，比滚动发布（按 Pod 批次替换、命中即接真实流量）影响面更小，且超阈值秒级自动回退。
- **stable/canary 双 Service**：Argo Rollouts 维护两个 ReplicaSet（stable 旧版 + canary 新版），通过 Service selector + 副本比例实现流量切分（20% 权重 = canary RS 副本数占比）。
- **AnalysisTemplate 指标驱动**：每步查 Prometheus SLO 指标——错误率（5xx 占比 ≤5%）与 P99 延迟（≤800ms），超阈值自动 abort 并回滚到上一个 stable ReplicaSet。判断依据是 SLO 指标而非 Pod Ready——Ready 只说明进程活着，不代表"对用户没伤害"。
- **阈值比 SLO 宽**（SLO 错误率 0.1%、金丝雀 5%）：新版本刚切流样本少，5% 是"明显有问题"的硬阈值，避免样本噪声误杀正常发布。

**版本区分**：`app/Dockerfile` 加 `ARG BUGGY=false` + ldflags 注入 `-X github.com/sre-demo/ordersvc/internal/handler.buggy=${BUGGY}`；`handler.go` 在 `buggy=="true"` 时 createOrder 50% 返回 500，用于构建 v3-bad 坏版本验证自动回滚（正式版本不编译此 flag）。脚本 `deploy/scripts/canary-deploy.sh` 封装"远程构建推 KECR + patch image 触发 + 观察进度"。

> **面试点**：金丝雀比滚动发布安全在哪？——滚动发布发现问题只能人工 rollback，中间窗口故障影响所有命中新 Pod 的用户；金丝雀按流量比例切流、每步指标 gate、超阈值秒级自动回滚到 stable，故障被限制在部分流量内。详见 `deploy/manifests/rollout-ordersvc.yaml`。

> **面试点**：混沌工程的价值？——主动制造故障验证假设，而非等真实故障才发现短板。Chaos Mesh 是 CNCF 项目，K8s 原生 CRD，声明式定义实验，可定时（cron）持续验证。

## 7. 故障自愈机制

| 机制 | 实现 | 愈合什么 |
|---|---|---|
| livenessProbe | /healthz 失败 3 次重启 | 进程死锁/泄漏 |
| readinessProbe | /readyz 失败摘流量 | 故障时自动隔离（注入失败率>0.9 标记 NotReady） |
| startupProbe | 慢启动保护 | 启动期不被 liveness 误杀 |
| HPA | CPU>60% 或 in_flight>10 扩缩 | 流量突增容量弹性 |
| 滚动发布 | maxUnavailable=0 | 零宕机变更 |

> **面试点**：liveness vs readiness 区别？——liveness 失败重启容器（进程级自愈）；readiness 失败只摘流量不重启（故障隔离）。readiness 失败时 Pod 还在但不收流量，等恢复再接回。

### 7.5 SLO Operator：slo-spec 升级 CRD（自研 K8s Operator，★★★）

把 SLO 规则从"手写 ConfigMap"升级为"CRD 声明 + controller 派生"，从"用工具"到"造工具"：

- **自定义 CRD `SLO`**（`slo.sre-demo.io/v1`）：spec 映射 slo-spec 结构（service/slos[]，每个 slo 含 objective/SLI/alerting），controller-runtime + kubebuilder 全套（CRD + controller + validating webhook）。
- **Reconcile 派生规则**：SLO CR → 5 窗口 recording rules（`ordersvc:{request_rate,error_rate,error_ratio,burn_rate}{5m,30m,1h,6h,1d}` + `latency_p99_5m`）+ 3 档 alert（Page 14.4/Ticket 6/Budget 1）。严格保住 slo-report.py 依赖的 4 个 rule 名。
- **双写降级**：派生结果双写 PrometheusRule CRD（主）+ ConfigMap（降级，裸 Prometheus rules volume 加载），CRD 未装也不阻断。
- **统一规则来源**：controller 跨 ns 写 `observability/prometheus-rules` ConfigMap 覆盖原手写规则，消除 ConfigMap/PrometheusRule 双份不一致。
- **validating webhook**：校验 objective/SLI/{{.window}}，**强制 `code=` 禁 `status=`**（修复 slo-spec.yaml `status=~"5.."` 与 metrics.go `code` label 不一致的同源 bug，正是金丝雀 AnalysisTemplate 那个 bug 的根因）。
- **代码**：`operator/` 独立 module（controller-runtime v0.19 + k8s client-go v0.31），`api/v1` types 手写等价 kubebuilder 生成结构 + deepcopy，`internal/controller` rule_generator + reconcile。本地 go build/vet 通过。

> **面试点**：为什么自研 Operator？——SLO 规则手写 26 条易错（status/code bug 就是手写出的问题），Operator 让"改 SLO 目标只改 CR"规则自动派生，且 webhook 准入校验防错。证明 Go+K8s controller-runtime 硬代码能力，不是只会 helm install。

### 7.6 告警智能分诊+自动修复 remediator（★★★★，2024-2026 AIOps 最热方向）

填补"只有探针/HPA/金丝雀被动自愈、无告警驱动主动修复"空白。Alertmanager webhook → 分诊服务（规则引擎自愈 + LLM 根因推断）：

- **作为 Alertmanager webhook receiver**：page/ticket 告警先送 remediator（`continue:true`）再送飞书通知。
- **智能分诊**：按 alertname/slo/severity 分组去重、关联 runbook_url、查 Prometheus 评估错误预算消耗（burn_rate5m/1h）、定级 P0-P3、生成幂等事件（hash(groupKey+startsAt)）。
- **自动修复规则引擎**：编码 runbook 决策树 4 规则——R-A1 `fault_reset`（调 /admin/fault 复位故障注入）/ R-B1 `scale_up` / R-C1 `scale_up` / R-D1 `rollout_undo`（危险）。按 burn5m 降序匹配取首。
- **8 条安全护栏**：cooldown 去重、危险动作 LLM+规则双确认（`RecommendRollback && Confidence≥0.7`）、chaos 只分诊不修复、动作白名单、scale 上限 20、LLM 只读不执行、DryRun 模式、审计日志。
- **LLM 根因推断**：调金山云大模型 glm-5.1（OpenAI 兼容 API），prompt 含告警 + Prom 指标 + Loki 日志摘要 + RAG 检索 runbook 知识，输出结构化 JSON（根因假设/scenario A-D/处置建议/是否回滚/置信度）。LLM 只读建议，不直接执行危险动作。
- **动作执行**：scale 走 clientset UpdateScale，rollout undo 走 kubectl patch status.abort（镜像内置 kubectl）。
- **代码**：`remediator/` 独立 module，`internal/{triage,remediate,llm,handler,prom,loki,k8s,metrics}`。LLM_API_KEY 走 Secret 注入（绝不入库）。本地 go build/vet 通过。

> **面试点**：为什么 LLM 只做根因推断不执行？——LLM 有幻觉风险，生产不可让模型直接动手改基础设施。安全动作（fault_reset/scale）走规则引擎自动执行，危险动作（rollout undo）需 LLM 建议 + 规则确认双保险。这是 AIOps 落地的正确姿势：人/规则保底，AI 辅助决策。

### 7.7 进化功能：错误预算策略 + LLM RCA + 混沌稳态校验

把平台从"被动监控"推进到"主动治理+自动闭环"：

1. **错误预算策略自动化**：remediator 定时查 burn_rate1d，预算耗尽（>1）自动 patch Argo Rollout `spec.pause=true` 冻结发布，预算恢复（<0.5）解冻。体现"错误预算驱动变更策略"——预算不够就不许发，从源头防故障扩大。
2. **LLM RCA 自动生成 postmortem 草稿**：事件 resolved 后喂 LLM（事件+根因+修复动作+时间线）按 postmortem/template.md 结构生成草稿，落 ConfigMap 供 validate-postmortem.py 校验。体现"自动闭环运营"——故障恢复即自动产出复盘草稿。
3. **混沌稳态校验**：Chaos Mesh PodKill 实验 + Argo AnalysisRun 自动校验 SLO 稳态假设（burn_rate5m ≤ 1），实验击穿 SLO 连续 2 次超阈值自动标记 Failed。体现"稳态假设驱动混沌"——不靠人肉看大盘。

### 7.8 灾备 + IaC + 成本可视化（★★，可治理/FinOps）

## 9. 面试讲解要点（按这个顺序讲，3 分钟讲清）

1. **背景**：传统运维稳定性靠感觉，我想用 SRE 方法论量化它。
2. **SLO**：定义可用性 99.9% + 延迟 P99 500ms，算出月错误预算 43 分钟。
3. **告警**：不用阈值，用多窗口多燃烧率——5m&1h 双窗口 > 14.4 才 Page，既快又不抖。
4. **可观测性**：Prometheus 指标 + Loki 日志 + Jaeger 链路三支柱，Grafana 统一大盘。
5. **混沌**：Chaos Mesh 注入 Pod Kill/网络/CPU，验证自愈和 HPA。
6. **自愈**：三探针 + HPA + 零宕机发布。

8. **成果**：MTTD ~30s，Pod Kill 30s 自愈不击穿 SLO，坏版本金丝雀秒级回滚。

### 高频追问预设
- **"错误预算用完了怎么办？"** → 冻结非紧急变更，专心保稳；和产品沟通降低 SLO 或加资源。
- **"SLO 怎么定？"** → 基于用户期望 + 历史数据 + 成本权衡，不是越高越好。
- **"为什么不直接 CPU>80% 告警？"** → 阈值告警不知道业务影响；燃烧率告警直接关联 SLO，只有预算真在烧才报。
- **"Prometheus 单点怎么办？"** → demo 用单实例；生产用 Thanos/Cortex 做高可用+长期存储。
- **"HPA 基于 CPU 够吗？"** → 不够，所以加了基于 `orders_in_flight` 的 Pods 指标扩缩，业务感知更准。

## 11. 项目体现的 SRE 思维（价值观层）

### 12.5 金丝雀自动回滚实测（变更安全验证）

用编译期注入 50% 500 的 v3-bad 版本验证坏版本自动回滚（Argo Rollouts）：

1. **buggy 生效确认**：exec 进 v3-bad pod 直接 curl `/order`，10 次请求 8 次返回 500——buggy 标志经 ldflags 注入生效，问题不在镜像。
2. **触发金丝雀**：v2 stable → patch image 到 v3-bad → canary 20%（1 个 v3-bad pod + 4 个 v2 stable），loadgen（busybox）持续打 `ordersvc-canary:8080/order`。
3. **指标检测**：错误率随 v3-bad 收到流量升至 **0.33（33%）**，远超 5% 阈值。
4. **自动回滚**：AnalysisRun 转 **Failed** → v3-bad ReplicaSet 副本数缩到 0 → 回滚到 v2 stable → Rollout 恢复 Healthy。

| 阶段 | 实测 |
|---|---|
| v3-bad canary 错误率 | **0.33**（阈值 0.05） |
| AnalysisRun | Running → **Failed** |
| v3-bad RS 副本数 | 1 → **0**（自动缩容回滚） |
| Rollout phase | Progressing → Degraded → **Healthy**（回滚后） |

**关键踩坑**：AnalysisTemplate 初版 PromQL 写 `status=~"5.."`，但指标 `ordersvc_http_requests_total` 的状态码 label 名是 `code`（见 `app/internal/metrics/metrics.go` 定义）——label 名对不上匹配到空 series，叠加查询末尾 `or vector(0)` 兜底返回 0，错误率恒为 0，导致 Analysis 永远 success、**永不回滚**。修复：PromQL 改 `code=~"5.."`，重测错误率立刻读到 0.33 触发回滚。教训：`or vector(0)` 这类无流量兜底是双刃剑，会掩盖"label 写错查不到数据"的真实故障；canary 健康分析的 PromQL 必须和指标 label 名逐字核对，先在 Prometheus 手动验证查询有值再放进 AnalysisTemplate；"分析一直成功"本身就是可疑信号。
